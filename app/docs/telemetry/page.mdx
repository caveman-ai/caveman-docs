The `caveman` CLI sends an anonymous event when a command finishes: which command ran, how long it took, whether it succeeded, and how many tokens the local proxy processed and cut since the last event. It is on by default in an interactive terminal, off everywhere else, and three switches turn it off for good. Prompts, code, file paths and model names are never part of it. Caveman Blocks sends its own usage counts and shares the CLI's consent; see [Caveman Blocks](#caveman-blocks).

```bash
caveman telemetry status
```

```json
{
  "enabled": false,
  "state": "off",
  "source": "runtime",
  "anonymous_id": "…"
}
```

That run was piped, so `source` reads `runtime`: a non-interactive shell turns telemetry off on its own. In a real terminal after a decision has been stored, `source` reads `config`; with an environment override in play it reads `env`. The `anonymous_id` is a random UUID minted on your machine and is shown in full when you run it.

## The three off switches

```bash
caveman telemetry off              # writes the decision to the CLI's config file
export DO_NOT_TRACK=1              # any value except empty or 0
export CAVEMAN_TELEMETRY=0         # anything except 1, true, or on means off
```

A stored decision is honoured forever, including a "no" given to an older version of the prompt. An environment override beats the stored decision, so `DO_NOT_TRACK` silences a config that says on, and `caveman telemetry on` under an active override tells you so and still sends nothing until you unset it.

Turn it back on with `caveman telemetry on`. That is the one moment a `consent_granted` event fires, carrying the anonymous id, the CLI build, the platform and a timestamp.

## When it is off without you asking

- **Continuous integration.** A truthy `CI` environment variable turns it off.
- **Not a terminal.** If either stdin or stderr is not a TTY, it is off. Piping, redirecting and running from a script all land here.
- **Help and version.** `caveman help`, `caveman version`, `--help` and `-h` skip the decision and the send.
- **Before the decision is on disk.** The first interactive run writes the decision, prints the disclosure line to stderr, and only then is anything sendable. A read-only home directory means the write fails, and the CLI stays silent from there on.

The disclosure it prints, once:

```text
anonymous usage stats on — command counts and token totals only, never prompts, code, or file paths · caveman telemetry off
```

## What one event contains

Events go to `https://api.caveman.so/telemetry/cli` as a JSON array, with a 1.5 second timeout, and a failed request is dropped rather than retried. `CAVEMAN_TELEMETRY_URL` points them somewhere else if you want to see them yourself.

| Field | What it is |
|---|---|
| `schema` | The event schema, `cli/v1`. |
| `event` | `command_run`, `runtime_bootstrap`, or `consent_granted`. |
| `anonymous_id` | The random UUID stored in your config. |
| `command` | The verb, from a fixed allowlist. A verb not on the list is reported as `unknown`. |
| `subcommand` | The second word, also from a fixed allowlist, when it matched one. |
| `agent` | The agent id for a wrap or run, when the command named one. |
| `cli_version`, `os`, `arch`, `node_major` | The build and the platform. |
| `duration_ms` | Wall time for the command. |
| `exit_class` | `ok` or `error`. |
| `error_class` | On an error: `network`, `auth`, `usage`, `unknown_command`, `exec_failed`, or `other`. |
| `ts` | An ISO timestamp. |
| `tokens_processed`, `tokens_saved`, `tokens_basis` | On `command_run` only, when the local proxy has a store to read. |

A complete event, with the fields that vary by machine replaced by `…`:

```json
{
  "schema": "cli/v1",
  "anonymous_id": "…",
  "event": "command_run",
  "command": "stats",
  "cli_version": "…",
  "os": "darwin",
  "arch": "arm64",
  "node_major": 22,
  "duration_ms": 412,
  "exit_class": "ok",
  "ts": "…",
  "tokens_processed": 18422,
  "tokens_saved": 4106,
  "tokens_basis": "inferred"
}
```

## The token fields

`tokens_processed` and `tokens_saved` are deltas, not totals. The CLI asks the local proxy for its lifetime aggregate with `caveman-proxy stats --json`, subtracts a watermark stored in the same config file, and advances the watermark. Three consequences:

- The first read on a machine seeds the watermark and reports nothing, so the event carries traffic from after the disclosure only.
- A store that went backwards, because the database was deleted or restored from a backup, re-baselines rather than reporting a negative or a second copy of history.
- A dropped request loses that delta instead of replaying it. Undercounting is preferred to double counting a savings number.

`tokens_basis` carries the basis word with the number, which is `inferred` for every local store. The receiving side cannot promote it. See [Numbers and limits](/docs/counting#inferred).

Reading the aggregate means spawning `caveman-proxy`, which runs after the command's own work with a 400 millisecond budget. A slow or wedged binary drops the token fields and the event ships without them.

## What it never contains

The table above is the whole event: an allowlisted verb (anything else ships as the literal string `unknown`), a build, a platform, a duration, an outcome and two token counts, which leaves prompts, responses, code, file paths, repository names, model names, provider names and API keys out of it entirely.

Two neighbours are separate systems. The [installer](https://github.com/JuliusBrussee/caveman/blob/main/INSTALL.md) sends Caveman telemetry nowhere, though it shells out to per-agent CLIs that reach their own registries. `caveman sync` uploads span metadata to a connected organisation's dashboard, and runs only when you are logged in and ask for it.

## Verify and undo

```bash
caveman telemetry status   # state, source, and your anonymous id
caveman telemetry off      # and it stays off
```

`status` is the one telemetry verb that leaves the decision unmade, so running it on a fresh machine shows you what would happen while leaving the machine as it was.

## Caveman Blocks

`caveman-blocks` sends its own usage counts under the `blocks/v1` schema. Like the CLI, it is on by default and stays silent until a disclosure has been shown and the choice saved. Every field is a number, a boolean, or a string checked against a fixed list or format, so scripts, shape fingerprints, commands your agent ran, file paths, repository names or remotes, block parameters, block output and the names of blocks you wrote have nowhere to go. Names of first-party blocks such as `json-peek` and `test-summary` are sent, because that list is public and fixed.

```bash
caveman-blocks telemetry status   # on or off, why, and your install ID
caveman-blocks telemetry off      # off for good on this machine
caveman-blocks telemetry on       # only works from a terminal
```

### Off switches, in precedence order

1. `DO_NOT_TRACK` set to anything except empty or `0`.
2. `CAVEMAN_BLOCKS_TELEMETRY` set to anything except empty, `1`, `true` or `on`.
3. `CAVEMAN_TELEMETRY`, the CLI's switch, read the same way. It can turn Blocks off, never on.
4. `CI` set to anything except empty, `0` or `false`.
5. A choice saved with `caveman-blocks telemetry on|off`. A saved `off` is honoured forever.
6. An opt-out saved by the CLI with `caveman telemetry off`.

Anything not on that list leaves the default, on. Only a person at a terminal can turn it on: `telemetry on` refuses anywhere else, while an agent or a script can always turn it off. When an interactive command sees switch 1, 2 or 3, Blocks also saves a lasting `off`, because hooks started by desktop apps often never read your shell profile.

Off also covers what was counted while it was off. Any `caveman-blocks` process that finds telemetry off, the hook included, marks the day, and a marked day is never sent, nor any day before it, even after telemetry is back on. `CI` on its own is the exception: it stops that process from sending and marks nothing, because some agent harnesses set it for every command.

### The disclosure and shared consent with the CLI

The first interactive command, meaning stdin and stderr are both a terminal and no agent harness variable such as `CLAUDECODE`, `CURSOR_AGENT` or `GEMINI_CLI` is set, prints this line once on stderr and saves the choice:

```text
usage counts on · commands, hints shown and followed, block runs, a random install ID, OS and your IP address · never scripts, file paths, repo names or names of blocks you wrote · this is what keeps Blocks free · off: caveman-blocks telemetry off · https://github.com/caveman-ai/blocks/blob/main/docs/TELEMETRY.md
```

Commands without a terminal, including the hook and anything an agent runs, never save the default on their own. `help`, `version`, `telemetry status` and `telemetry off` never print the line.

The CLI's notice covers Blocks from disclosure version 6 onwards. While the CLI has telemetry on under that notice, any `caveman-blocks` process saves the default silently and reuses the CLI's install ID. That includes the hook and `hooks install` run by `caveman on scripts`. One notice means one opt-out: `caveman telemetry off` turns both off, and `caveman-blocks telemetry status` reports `covered by the Caveman CLI's telemetry`.

When the CLI has telemetry on, a Blocks install enrolled from its own disclosure reuses the CLI's install ID too, and the disclosure line adds `shares the Caveman CLI install ID`. If the CLI later turns telemetry off or replaces its ID, Blocks drops the shared ID at once, marks the day off, and sends nothing until the default is saved again. `caveman-blocks telemetry off` deletes the install ID from disk and prints it once, because it is the only key to a deletion request.

### Events

Each flush is one HTTPS `POST` of a JSON array of at most 20 events. Every event carries these fields:

| Field | What it is |
|---|---|
| `schema` | The event schema, `blocks/v1`. |
| `event` | `first_run`, `command_run`, or `daily_usage`. |
| `ts` | An RFC 3339 UTC timestamp. |
| `anonymous_id` | The install ID. |
| `cli_version`, `os`, `arch` | The build and the platform. |
| `install_channel` | `npx`, `brew`, `direct`, or `source`. |
| `linked` | `true` when the install ID is shared with the CLI. |

- **`first_run`** is sent once when telemetry starts under an install ID. An install enrolled under the CLI's notice sends exactly one, from whichever process enrols first. It has no further fields.
- **`command_run`** is sent after each interactive command. Commands run by agents or scripts send none. It adds `command` (from a fixed list, otherwise `unknown`), `subcommand`, `block` (for `add` and `run`, only when the block is first-party), `duration_ms`, `exit_class` (`ok` or `error`), `error_class` (`usage` for exit 2, `failed` for any other non-zero exit) and, for a successful `scan`, `scan_*` counts of commands, scripts and shapes.
- **`daily_usage`** is one row per install per UTC day with activity, summed across every repo on the machine from the `stats.jsonl` files the hook and runner already write. Only complete past days are sent, oldest first, at most 7 days back.

| `daily_usage` field | What it is |
|---|---|
| `day` | The UTC day counted, `YYYY-MM-DD`. |
| `repos_active`, `sessions` | Repos with activity, and agent sessions the hook saw. |
| `scripts`, `scripts_bytes` | Inline scripts captured, and their size in bytes. The scripts stay on the machine. |
| `hints`, `hints_followed`, `promote_hints` | Hints shown, hints followed by a call of the hinted block, and promotion suggestions shown. |
| `calls`, `runs`, `runs_failed`, `runs_user` | Block calls, runs, failed runs, and runs of blocks that are not first-party. |
| `verify_pass`, `verify_fail` | Verify outcomes. |
| `bytes_full`, `bytes_returned` | Output bytes blocks produced, and bytes returned to the agent. |
| `blocks_first_party`, `blocks_user` | Distinct first-party and other blocks run. Only the count of other blocks is sent. |
| `first_party_runs` | First-party block name to run count. |
| `harness_sessions` | Harness (`claude`, `codex`, `cursor`, `generic`) to distinct sessions. |

### How it is sent

After an interactive command, `caveman-blocks` starts a detached `caveman-blocks telemetry flush` and exits. The hook starts the same process at most once every 24 hours. The flush hands the JSON to the system `curl` with a 10 second timeout, so a machine without `curl` sends nothing. A failed send never fails or slows a command, and unsent days are retried on the next flush. `CAVEMAN_BLOCKS_TELEMETRY_URL` overrides the destination for testing; it must be an `https://` URL or `http://` to `127.0.0.1` or `localhost`.

Events land in the same backend as the CLI's telemetry, which stores them with the time received and the sender's IP address, used to rate-limit. IP addresses are cleared after 90 days and events are deleted after 13 months. To have every stored event for your install deleted, send the install ID to security@caveman.so with "telemetry deletion" in the subject.
