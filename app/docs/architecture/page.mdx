One request leaves your agent, passes through a rule file and a local proxy, and reaches your provider smaller than it started. This page follows that request, names the part that acts at each hop, and shows where the removed bytes are kept.

## Before and after

The engine is the compressor. Feed it a 65 line build log on stdin and the smaller view goes to stdout while the report goes to stderr, so a redirect keeps the two apart:

```bash
caveman-engine compress < build.log > small.log
```

## One request, end to end

<RequestPath />

Four hops, and one of them runs backwards. The skill shapes what the agent decides to say. The engine shapes what the payload weighs. The provider bills for whatever arrives. The dashed line is a recovery: something the engine left out, asked for again.

How much that recovery costs depends on which path is doing it. Where the proxy injected its own retrieve tool, the proxy answers the call from the local store and continues the same agent turn: the agent issues no second request, and the provider calls that continue the exchange are made and metered by the proxy, up to three retrievals. Where the agent holds the [MCP](/docs/mcp) tool itself, it calls the local store directly. In the [middleware](/docs/sdk/middleware/deployment#what-to-measure), a recovery is a real extra provider call your application makes and pays for, which is why that page tells you to count it.

## Where the skill acts

Before the request exists. The skill is an instruction file the agent reads at session start, so it changes the agent's own output: fewer preambles, fewer restatements, fewer closing summaries. It is text, not software, and there is no process to run.

It is explicit about what it copies through byte for byte, and about the moments where it drops back into full sentences. [What it leaves alone](/docs/skill#what-it-leaves-alone) is that list.

## Where the proxy acts

<ProxyPath />

After the agent has decided what to send and before the bytes leave your machine. The proxy listens on `127.0.0.1:8787` by default, forwards to the provider you configured, and passes your credentials through untouched. Inside it, the engine runs on each eligible segment:

1. **Detect the content type.** `detect()` types the payload from its bytes alone. `caveman-engine registry` lists the types it knows: JSON, log, code, diff, search result, table, config, terminal output, tool schema, text, HTML, accessibility tree, repetition and TOON.
2. **Look up the compressor** for that type. A type with no compressor registered is forwarded unchanged.
3. **Check the safety class.** A compressor that loses bytes carries `RequiresCCR`, so it may only run when the original can be written to the recovery store first.
4. **Store the original, then publish.** The original goes to the store, and only after that write succeeds does the smaller view leave with its handle. Output that is not smaller than the input is dropped and the original goes instead.

Those four are the ones that decide what reaches the provider. The engine runs three more around them, unwrapping presentation and counting both sides; [The pipeline](/docs/proxy/engine#the-pipeline) has all seven in order.

Two local databases sit under the proxy. The usage store holds one `inferred` row per request, which is what [`caveman stats`](/docs/cli) reads. The recovery store holds original bytes. Neither holds a provider bill. [The engine](/docs/proxy/engine) has the per-compressor detail.

## Where recovery lives

In a SQLite file on your machine. The default is `~/.caveman/ccr.db`, and `CAVEMAN_CCR_DB` points somewhere else. The original is written under a content-addressed handle before the compressed view is emitted, so a handle always resolves:

```bash
caveman-engine retrieve ccr_0d3b5b5c431246dc87f7e3d1ad00ee11 | diff - build.log && echo identical
```

```
identical
```

The agent reaches the same store through the [MCP server](/docs/mcp)'s `caveman_retrieve` tool, and the CLI through `caveman retrieve`.

The store is a hard dependency of any lossy result, and it fails in two different ways. A store that cannot be opened stops the command: `caveman-engine` exits 1 with `cannot open recovery store: …` and writes nothing to stdout. A store that opens but will not take the write returns the accounted pass-through result together with an error: the CLI writes the original to stdout and puts `"error": "cave_ccr_unavailable"` in the report, with `"ratio": 0`. Either way a smaller payload is never emitted without its original behind it. [Recovery](/docs/proxy/recoverable#when-compression-refuses-to-run) has both cases with their reports.

Compression is skipped, and the original bytes are forwarded, in five cases: record mode is on, no compressor claims the content type, the compressor cannot parse the payload, a lossy compressor has no recovery store to write to, or the result came out the same size or larger. [Recovery](/docs/proxy/recoverable) covers each one.
