LiteLLM and the proxy take different seats. LiteLLM holds provider keys, translates provider APIs, and
enforces budgets per virtual key. The proxy shrinks what an agent rereads and keeps the originals
recoverable. Put the proxy where the bytes are largest, which is between the agent and LiteLLM, or behind
LiteLLM as a deployment's `api_base`.

## Before either path

A bare `caveman start` resolves to record mode so an unattended listener does not transform traffic. Set
compression first, then start.

```bash
caveman tools config set think.mode compress
caveman start
```

The listener is `http://127.0.0.1:8787`. A non-loopback bind requires inbound token authentication; see [Shared proxy](/docs/proxy/shared).

## Per call

Point one call at the proxy. The provider key travels on the request and the proxy forwards it.

```python
import os
import litellm

res = litellm.completion(
    model="openai/gpt-5.5",
    api_base="http://127.0.0.1:8787/openai/v1",
    api_key=os.environ["OPENAI_API_KEY"],
    messages=[{"role": "user", "content": "Why is the sky blue?"}],
)
```

Anthropic models use the `/anthropic/v1` mount and Gemini `/gemini/v1beta`. Every route is on
[Providers](/docs/proxy/providers). The CLI prints this snippet with the right mount:

```bash
caveman snippets litellm
```

## Fleet-wide, behind LiteLLM

Every client behind a LiteLLM proxy inherits what a deployment declares. Point the deployment at the
proxy instead of the provider.

```yaml
model_list:
  - model_name: gpt-5.5
    litellm_params:
      model: openai/gpt-5.5
      api_base: http://127.0.0.1:8787/openai/v1
      api_key: os.environ/OPENAI_API_KEY
```

Loopback works when both processes share a host or pod. A separate private-network proxy requires its inbound token in addition to the upstream provider credential.

<Note tone="honest" title="Recovery on this path">
A client on another machine has no Caveman MCP tool, so it cannot recover an original itself. On this
path the proxy compresses only where it can handle recovery on its own side, which today means
non-streaming API-key requests on adapters that support it. Streaming sessions pass through unchanged.
The rule is on [Wrap an agent](/docs/proxy/wrap).
</Note>

LiteLLM records what the provider reported, which is the compressed request. Its spend view reflects its configured accounting; it is not an invoice reconciliation. `caveman stats` shows what was removed, labelled `inferred`, and the two are never added.

## In front of LiteLLM

For an agent that runs where the proxy runs, put the proxy first and let LiteLLM stay the thing that talks
to providers. Declare LiteLLM as a compatibility mount and allow it as an upstream.

```yaml
# ~/.caveman/caveman.yaml
compat:
  litellm:
    base_url: http://litellm.internal:4000
    api_key_env: LITELLM_VIRTUAL_KEY
```

```bash
caveman tools mcp install claude --server caveman
CAVE_SSRF_ALLOWLIST=litellm.internal caveman start
ANTHROPIC_BASE_URL=http://127.0.0.1:8787/compat/litellm claude
```

A compat mount serves two wire protocols from one upstream. A request to `/compat/litellm/v1/messages`
carries the key in `x-api-key`; every other path carries `Authorization: Bearer`. Claude Code appends
`/v1/messages`, so it lands on LiteLLM's Anthropic-format endpoint. Private and loopback upstreams are
blocked until the exact host is in `CAVE_SSRF_ALLOWLIST`; see [Security](/docs/proxy/security).

A Claude Pro or Max login cannot cross LiteLLM. This path needs an API-key backed virtual key. For
subscription auth, drop LiteLLM and run `caveman claude`.

`cache_control` markers a client sent are forwarded unchanged. Compression changes tool-result bodies, which
sit after the cached prefix in a normal agent request.

## Model decisions: caveman-router

`caveman-router` is an MIT Python package that registers as a LiteLLM callback. On each chat request it asks
for a deployment alias and changes only that. Keys, inference, streaming and retries stay with LiteLLM.

```bash
python -m pip install .            # from the package directory, in LiteLLM's environment
export CAVE_API_KEY='project key with router:write'
caveman-router setup --config config.yaml
caveman-router check --config config.caveman.yaml
litellm --config config.caveman.yaml
```

`setup` writes `config.caveman.yaml` beside the original, puts the callback first in
`litellm_settings.callbacks`, and refuses fewer than two distinct chat models.

The callback leaves a request as sent when it carries `tools`, `response_format`, `reasoning_effort`,
`thinking`, audio, `logit_bias`, a `previous_response_id`, or any provider pin such as `api_base` or an
Azure, Bedrock or Vertex field. It intersects candidates with the virtual key's allowed models before
asking and re-runs LiteLLM's authorization check on the answer. The decision has a wall-clock deadline of
150 milliseconds by default. On timeout, HTTP error or an invalid answer the requested model is kept and
one warning is logged. At most 8 KB of prompt text leaves; tool results, headers and tenant identifiers do
not.

The decision endpoint is part of Caveman Cloud. The package and its conformance tests against a real
LiteLLM server are public; the first three sections need no account.

## Measured

Direct Claude Code against the wrapped proxy on six tool-heavy tasks, three runs each: 885,793 to 591,673
provider-reported input tokens, a 33.2 percent reduction, 18 of 18 exact answers, one HTML case at
minus 9.9 percent. Basis `benchmark_counterfactual`. The gateway hop changes neither number.
