Every byte a lossy compressor removes is written to a local store before the smaller view is emitted, keyed
by a handle derived from the original's own SHA-256. `retrieve(handle)` returns those bytes exactly, and
where the store is unreachable or full the original payload travels on as the caller sent it. The store is
called CCR, Caveman Context Recovery, and it is a plain SQLite file under `~/.caveman`.

## Compress, then get it back

```bash
curl -O https://docs.caveman.so/examples/engine/app.log
caveman-engine compress < app.log > smaller.log 2> report.json
cat smaller.log
```

## The handle

`ccr_` followed by the first 16 bytes of the original's SHA-256, as 32 lowercase hex characters. Nothing
else goes into it, so the handle is a name for the content rather than for the event that stored it:

```bash
shasum -a 256 app.log | cut -c1-32
```

```text
af97d456aad47eab01cdcdd56688a39e
```

Two consequences follow. Compressing the same payload twice returns the same handle and stores one row,
which is what keeps a repeated tool result from filling the store. And a handle minted on one machine names
the same bytes on another, though it only resolves where those bytes were stored.

Several short-lived processes share one file, so the connection opens with `journal_mode(WAL)` and
`busy_timeout(5000)` and keeps a single writer. Both pragmas are part of the contract rather than tuning:
they are what keeps a reader resolving a handle while another process writes, and what keeps that write
durable, which is the pair a compressed payload's honesty rests on.

Rows are kept rather than evicted because a request already on the wire can reference any handle. Evicting
an old original to make room would turn a compression that was honest at the time into an unrecoverable one
afterwards. When the budget is reached the engine stops compressing instead.

## Two stores

The framework middleware writes here too, and puts a second name in front of it. A call optimized through
`/caveman/v1/middleware/*` stores its original as an ordinary `ccr_` row, then hands the application a
random `cmw_` grant that maps to that row and resolves only under the conversation scope it was minted for.
The grant expires 24 hours after the last optimize or retrieve that touched that scope, and a retrieve after
that answers `expired`, while the `ccr_` row it pointed at stays, because nothing here is evicted.
[Middleware](/docs/sdk/middleware) is that path.

## How an agent asks

Two kinds of marker point at the store. Inside a compressed payload, the compressor leaves an elision
marker like the `… 39 lines elided (caveman) …` line above, which states what was removed and, once per
tool result, names `caveman_retrieve`. On the wire, the proxy appends `<<ccr:ccr_…>>` on its own line at
the end of each block it rewrote, so the handle travels with the content it replaced.

A tool named `caveman_retrieve` resolves those handles, and which one the agent sees depends on the path.
The proxy adds its own to the upstream request when it answers recovery calls itself:

```json
{
  "name": "caveman_retrieve",
  "description": "Recover original content for a compressed block. Use the handle shown in a <<ccr:...>> marker inside the content. Pass query only when a narrower recovery is enough.",
  "input_schema": {
    "type": "object",
    "properties": {
      "handle": { "type": "string", "description": "recovery handle from a <<ccr:...>> marker in compressed content" },
      "query": { "type": "string", "description": "optional: describe the detail you need; the proxy returns only the elided sections most relevant to it instead of the entire original block" }
    },
    "required": ["handle"]
  }
}
```

Read off the request a caveman-proxy build dated 2026-08-24 sent to a local stub upstream, with the key
order as it appeared; `caveman setup --install` today pins bin-v1.1.7, so digits may move. The proxy answers
at most three retrieve calls per request and stops inspecting an upstream response larger than 8 MiB,
raised with `CAVE_MAX_RETRIEVE_RESPONSE_BYTES`; past either bound it replays the original exchange to the
client. The [MCP server](/docs/mcp) publishes the same tool name with the argument spelled
`recovery_handle`, and normalises a bare `ccr_` handle, a full `<<ccr:HANDLE>>` marker, a `ccr:ccr_` prefix
and a native `ccr://` reference to the same lookup. Either way an unknown handle is an explicit error
rather than an empty result.

The `caveman-engine retrieve` command takes the bare handle only, and marker syntax is the MCP tool's job:

```bash
caveman-engine retrieve ccr_af97d456aad47eab01cdcdd56688a39e "connection reset"
```

```text
… [caveman: non-adjacent] …

2026-09-16T09:00:42Z ERROR worker.pool task failed id=t-2042 queue=ingest err=connection reset by peer

… [caveman: non-adjacent] …
```

With no query the original comes back byte for byte. With a query the stored content is split into whole
units, ranked by BM25 with a ceiling of 20 sections, and returned in original order. `… [caveman:
non-adjacent] …` stands wherever content was skipped, including at either end, because two units placed
side by side that were not neighbours in the source let a reader attribute a field to the wrong record.
A view that cannot be ranked, or that matches nothing, returns the whole original.

## When compression refuses to run

Each of these returns the input bytes unchanged with `ratio: 0` and no handle.

**No store.** A lossy compressor carries `RequiresCCR`, so it runs where a store is attached or where the
caller declared its own recovery. Anywhere else the engine hands back the original.

**Store unreachable.** Two cases. A store the CLI cannot open stops the command: it exits 1 with
`cannot open recovery store: …` and writes nothing to stdout. A store that opens but refuses a write returns
the original to stdout with `ratio: 0` and `"error": "cave_ccr_unavailable"` in the report.

**At the budget.** A write that would push retained bytes past the cap is refused before anything lossy is
published:

```bash
curl -O https://docs.caveman.so/examples/engine/big.json
CAVEMAN_CCR_MAX_BYTES=65536 caveman-engine compress < big.json > out.json 2> report.json
cmp big.json out.json && echo identical
```

```text
identical
```

```json
{
  "content_type": "json",
  "tokens_before": 22082,
  "tokens_after": 22082,
  "ratio": 0,
  "basis": "inferred",
  "error": "cave_ccr_budget_exceeded"
}
```

65,536 bytes is the smallest budget the store accepts, and `big.json` is 62,082 bytes of event records
whose original plus its recovery metadata clears it.

**Not smaller.** Output that counts the same or more tokens than the input is discarded and the original
goes on, leaving the store exactly as it was.

<Note tone="honest" title="Recoverable is not the same as harmless">
Recovery guarantees the bytes come back on request. It does not guarantee the model asks. A compressed view
that hides the one row an answer turned on costs a recovery round trip at best and a wrong answer at worst,
which is why every elision marker states facts computed from what it replaced instead of only a count. See
[All compressors](/docs/proxy/compressors#what-every-compressor-guarantees).
</Note>
