The proxy holds provider credentials and the full text of what your agent sends, so its defaults are the
narrow ones: it listens on loopback, reads every key from the environment at request time, rebuilds the
upstream header set from scratch, and refuses to dial private addresses. This page says where each of those
lines sits and what is on your disk afterwards.

The inbound token gate, the `cave_proxy_unauthorized_total` counter, and auth-before-routing ship from
binary release bin-v1.1.7. Run `caveman setup --install`, then check that `~/.caveman/bin/.bin-manifest.json`
reads `"release": "bin-v1.1.7"` or later before exposing a listener. `caveman version` reports the release the
CLI pins, not the one on disk. On an older binary a non-loopback bind is still refused, but a token on a
loopback listener is not enforced.

```bash
caveman start --host 0.0.0.0
```

```text
{"time":"…","level":"ERROR","msg":"cannot load caveman.yaml","error":"listen address \"0.0.0.0:8787\" is not loopback; standalone proxy has no inbound authentication; set CAVEMAN_AUTH_TOKEN to expose the proxy beyond loopback"}
```

The proxy exits at config load rather than putting every configured provider credential on the network.
Captured from caveman-proxy bin-v1.1.7 with the timestamp replaced by `…`.

The health payload under [Start it](/docs/proxy#start-it) reports `billing: byok`, which is the fact
underneath the rest of this page: the credential that pays for a request is one you supplied, held by this
process only for the moment it forwards.

## Who can reach it

The default listen address is `127.0.0.1:8787`, so only processes on your machine can connect. A wider bind
is refused at config load unless `CAVEMAN_AUTH_TOKEN` is set, in which case every request must present that
token in `x-cave-api-key` or `Authorization: Bearer`. [Shared proxy](/docs/proxy/shared) covers that
deployment.

`localhost` and any loopback IP count as local. Everything else, including `0.0.0.0`, is a wider bind.

## What happens to your keys

Keys live in the environment of the proxy process, and a key on the incoming request wins over that
environment. Either way the proxy builds the upstream headers from an allowlist of caller fields plus the
resolved credential in the header that provider expects: `x-api-key` for Anthropic, `Authorization: Bearer`
for OpenAI, `x-goog-api-key` for Gemini, `api-key` for Azure, a fresh SigV4 signature for Bedrock. A client's
own `Authorization` value reaches a provider only when the resolver chose it as the credential.

Caveman's own headers are stripped in both directions. Any inbound `x-cave-` or `x-caveman-` field is dropped
before the request goes upstream, and the same fields are dropped from the provider's response before it
reaches the client, along with the hop-by-hop fields a caller nominated in `Connection`.

The config file holds no secrets by design, and
[an `auth_token:` key in it stops the proxy from starting](/docs/proxy/configure#every-field).

## What gets logged

Every log line the proxy writes goes through a redactor before it is emitted, and errors from upstream are
redacted again on the way into a log field. The redactor covers bearer tokens of 20 characters or more,
`sk-` keys, AWS access key ids, PEM private key blocks, connection strings carrying credentials, and
assignments whose name contains key, secret, token or password.

Request and response bodies are outside the logging path entirely. A rejected inbound token is logged as the
path and the remote host, and the value that was presented stays out of the record.

## Where the proxy dials

Standalone mode runs the SSRF guard on every upstream connection, checking the resolved IP at the moment the
kernel connects rather than only at parse time. Loopback, link-local, metadata-service and private addresses
are blocked, so a malicious or mistyped `base_url` cannot turn the proxy into a way to reach an internal
host.

```bash
CAVE_SSRF_ALLOWLIST=localhost:11434 caveman start
```

That is the opt-in for a local model server or a LAN inference box. An entry is a bare hostname or
`host:port`, and `localhost` covers `127.0.0.0/8` and `::1`. Bedrock and Vertex pre-flight their resolved
endpoint against the same policy before the request is built. A dial the guard refuses reaches the caller as
`502 cave_upstream_unavailable`, and `proxy.log` stays silent, so a mount that answers 502 with an empty log
is the signature of a missing allowlist entry.

Link-local addresses, including the cloud metadata services at `169.254.169.254`, cannot be allowlisted in
any mode. Neither can multicast, the unspecified addresses, the documentation ranges, carrier-grade NAT or
the NAT64 prefixes. A reachable metadata service turns a proxy into a way to read cloud credentials, so those
ranges carry no opt-in at all.

Set `upstream_proxy` and provider traffic goes through your outbound HTTP proxy instead, with the destination
policy moving to that proxy's ACL. It applies to provider traffic only, so the wrapped agent's own tool
executions inherit nothing.

## What is on your disk

Everything sits under `CAVEMAN_HOME`, `~/.caveman` unless you set it, created with mode `0700`.

| File | Contents | Risk if read |
|---|---|---|
| `caveman.db` | One row per request: time, provider, model, endpoint, token counts, mode, SHA-256 of the bytes. | Metadata about your traffic. |
| `ccr.db` | The exact original bytes of everything compression removed. | Your prompts and tool output, in the clear. |
| `proxy.log` | Startup lines and warnings, redacted. | Endpoints and error text. |
| `run/<port>.json` | pid, port, mode, owner, instance token of the live listener. | Local process facts. |
| `receipts/`, `runtime/` | Per-session state for the installed agent hooks. | Session identifiers. |

Two opt-in paths widen that. `CAVE_CAPTURE_DIR` writes both sides of every transform to a directory you name,
as complete unredacted bodies, and it has no rotation and no expiry. [`caveman trial`](/docs/trial) stores
the raw request body of each request in the run it is measuring, in `caveman.db`, so a before-and-after
comparison can be replayed.

<Note tone="honest" title="ccr.db is the sensitive file">
Recovery means the original bytes are still there. Everything the engine folded out of a request, file
contents, logs, tool results, sits in `ccr.db` in the clear so the agent can ask for it back. It is a local
SQLite file with your user's permissions, and it deserves the same treatment as a shell history file.
</Note>

## Deleting it

```bash
rm ~/.caveman/ccr.db ~/.caveman/caveman.db ~/.caveman/proxy.log
```

Stop the proxy first, then delete. The next start creates empty stores. To keep the whole thing somewhere
else, or to give a project its own, set `CAVEMAN_HOME` before starting:

```bash
CAVEMAN_HOME=/tmp/caveman-scratch caveman start
```

`CAVEMAN_DB` and `CAVEMAN_CCR_DB` move the two stores individually.
