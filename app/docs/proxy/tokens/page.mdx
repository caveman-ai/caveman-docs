Every ratio the engine prints comes from one offline BPE tokenizer, `o200k_base`, whose vocabulary is
compiled into the binary. It counts the input, counts the output, and divides. Because it is a local
estimate of what a provider will bill rather than the provider's own count, everything it produces is
labelled `inferred`.

## Count one payload

```bash
curl -O https://docs.caveman.so/examples/engine/orders.json
caveman-engine compress < orders.json > /dev/null
```

```json
{
  "content_type": "json",
  "tokens_before": 1968,
  "tokens_after": 290,
  "token_count_basis": "o200k_base",
  "ratio": 0.8526422764227642,
  "basis": "inferred",
  "recovery_handle": "ccr_9ced906549d5622bb37187cee43afbd2",
  "method": "elision",
  "lossless_to_model": false
}
```

Captured from a caveman-engine build dated 2026-08-24; `caveman setup --install` today pins bin-v1.1.7, so
digits may move. Trimmed to the fields this page names. The report goes to stderr so stdout stays payload
bytes.

## Two levels of label

The report carries a `token_count_before` and a `token_count_after` object beside the bare counts, each
describing the count the tokenizer just made. Two vocabulary digest fields are cut here:

```json
"token_count_before": {
  "tokens": 1968,
  "backend": "tiktoken-go/o200k_base",
  "revision": "github.com/tiktoken-go/tokenizer@v0.8.0",
  "surface": "raw_text",
  "exact": true,
  "basis": "local_tokenizer",
  "status": "measured"
}
```

`"status": "measured"` there is a statement about the string, not about a bill: the tokenizer read those
exact bytes and the tiktoken count is exact, so the count itself is not an estimate. The payload-level
`basis` stays `inferred`, because what the report claims is a saving against a provider's charge, and this
machine never saw that charge. [Numbers and limits](/docs/counting#vocabulary) defines both words.

## The counter

`tokens.Default()` returns a real byte pair encoding tokenizer for OpenAI's `o200k_base`, the GPT-4o family
encoding, built on `github.com/tiktoken-go/tokenizer` v0.8.0. The vocabulary is linked into the binary, so
counting makes no network call and works on an air-gapped machine. The same bytes always yield the same
count, which matters beyond tidiness: a compressed block has to re-serialise identically on every later turn
or the provider's cached prefix breaks.

One encoding is used for every content type and every provider. Anthropic and Google tokenize differently,
so treat the absolute count as an approximation and the ratio between two arms of the same run as the number
worth reading.

If the embedded codec fails to load at startup, the shared counter becomes `approx-chars/4`, a
deterministic count of runes divided by four with a floor of one, and `token_count_basis` says
`approx-chars/4` from then on. That approximation errs low, so a reduction it reports is the conservative
version of the real one.

`token_count_basis` names the counter the engine loaded, which is the only thing that switch changes. A
codec error on one individual string also falls back to the same approximation for that one count, and the
basis still reads `o200k_base`, because the loaded counter did not change. Read the field as which
tokenizer this engine holds, not as a per-count guarantee.

The `Counter` interface is two methods, `Count([]byte) int` and `Name() string`. An embedder can supply a
per-provider tokenizer to `engine.New` without touching a single compressor, because compressors never count
anything themselves.

## How the ratio is computed

```text
tokens_before = Count(input)
tokens_after  = Count(output)
ratio         = (tokens_before - tokens_after) / tokens_before
```

Both sides count the whole payload as it crosses the boundary, including any `<file …>` wrapper or
line-number gutter that was stripped for detection and put back afterwards. Counting the stripped body
instead would credit the engine for bytes it did not remove.

The comparison also decides whether the transform ships at all. Output that counts the same or more tokens
than the input is discarded, the original goes on, and `ratio` stays 0 with no handle. That check runs on
token counts rather than byte length, so a transform that trades many short tokens for few long ones is
still judged on what a model will be charged for.

## Aggregate counts

`stats` sums the rows in the recovery store, so it covers everything this machine compressed through a
lossy transform, across sessions and processes.

```bash
caveman-engine stats
```

```json
{
  "totals": {
    "count": 2,
    "tokens_before": 3742,
    "tokens_after": 540,
    "ratio": 0.8556921432389096
  },
  "by_content_type": {
    "json": { "count": 1, "tokens_before": 1968, "tokens_after": 290, "ratio": 0.8526422764227642 },
    "log":  { "count": 1, "tokens_before": 1774, "tokens_after": 250, "ratio": 0.859075535512965 }
  },
  "basis": "inferred",
  "storage_bytes": 10178,
  "max_storage_bytes": 536870912
}
```

Captured from a scratch store holding two payloads. On a real machine the counts are larger and
`storage_bytes` varies, so read the shape rather than the values.

`count` is rows, so a payload compressed twice counts once: the handle is content-addressed and the second
compression updates the same row. `storage_bytes` is the exact retained payload and metadata total, not the
size of the SQLite file, and `max_storage_bytes` is the configured cap. Once the first is at or above the
second, a `"storage_full": true` field appears beside them and every later lossy transform returns its
input. Pass-throughs are absent from this table entirely, because nothing was stored for them.

## Limits

`inferred` is the only basis these tools emit, and provider-reported usage from your own response stays
authoritative for spend. [Numbers and limits](/docs/counting#vocabulary) defines the word and lists what
caveman will not do with a local figure.
