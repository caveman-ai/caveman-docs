The mode decides what the proxy is allowed to do to the bytes of a request. record forwards them unchanged,
compress runs the engine on eligible blocks and keeps the originals, pixel renders eligible text into an
image for models that read images cheaply. The proxy reads the mode once at startup and reports it on every
response.

```bash
CAVEMAN_MODE=compress caveman start
```

```text
{"time":"…","level":"INFO","msg":"cache-breakpoint planner enabled","mode":"frontier"}
{"time":"…","level":"INFO","msg":"caveman proxy listening","addr":"127.0.0.1:8787","mode":"compress","basis":"inferred","inbound_auth":"none"}
```

Captured from caveman-proxy bin-v1.1.7, with the timestamps replaced by `…`. The first line is the
cache-breakpoint planner, which `breakpoint_plan: off` removes.

## The modes

| Mode | What reaches the provider | Originals |
|---|---|---|
| `record` | The client's bytes, unchanged. This is the default. | Nothing is removed, so nothing is stored. |
| `compress` | Eligible blocks replaced by a smaller view plus a handle. | Stored in `~/.caveman/ccr.db`, byte exact. |
| `pixel` | Eligible text rendered to a PNG the model reads. | Stored in `~/.caveman/ccr.db`, byte exact. |
| `recommend`, `shadow`, `canary`, `active` | Accepted names. In this binary they take the provider-native transform path, which adds cache metadata and leaves model-visible bytes alone. | Nothing is removed. |

Anything else in `mode:` or `CAVEMAN_MODE` resolves to `record`, so a typo costs you compression rather than
your traffic.

compress needs a way back to the elided bytes before it will rewrite anything. That is either the
`caveman_retrieve` MCP tool in the agent's own session, or a retrieve tool the proxy injects into
non-streaming API-key requests it can follow. With neither available the request passes through untouched.
[Recovery](/docs/proxy/recoverable) has the rules.

`mode: compress` is the proxy's permission to rewrite eligible bytes, and the compression headers on a
response are the record of a request where it did. Four things send a compress-mode request through
unchanged:

- Recovery is unavailable for that request.
- Detection finds no compressible content type in the body.
- Rewriting would move the provider's cached prefix. See [Prompt caching](/docs/proxy/caching).
- The recovery store has reached `CAVEMAN_CCR_MAX_BYTES`, 536870912 bytes by default. At the cap
  compression stops and requests forward unchanged; stored handles stay recoverable and nothing is evicted.

pixel runs only for models on an allowlist, set with `CAVE_PIXEL_MODELS`, and passes everything else through.
[Pixel mode](/docs/proxy/pixel) covers which models and how to check it paid off.

## How the mode is chosen

The proxy reads `CAVEMAN_MODE` first and `mode:` in `caveman.yaml` second.

```yaml
# ~/.caveman/caveman.yaml
mode: compress
```

The two CLI doors resolve a mode before they launch it, and they start from different defaults.

| Door | Default | Overrides, in order |
|---|---|---|
| `caveman start` | `record` | `mode:` in `caveman.yaml`, then the global config, then `CAVEMAN_MODE` |
| `caveman wrap`, `caveman <agent>` | `compress` | the global config, then `CAVEMAN_WRAP_MODE`, then `--off` or `--pixel` on the command |

`caveman start` passes `CAVEMAN_MODE` to the proxy only when the global config or the environment named a
mode. Left alone it says nothing, which is what lets the proxy's own `caveman.yaml` decide.

```bash
caveman tools config get
```

```text
think.mode = compress  (default)
think.core = true  (default)
think.toon = true  (default)
think.shrink = true  (default)
think.pixel.models = []  (default)
think.pixel.density = balanced  (default)
```

The first six rows of that output; the rest cover memory and execution. The value in brackets is where it
came from, so `(default)` means nothing has been set and `(global)` means `~/.caveman-cloud/config.json` has.

## Telling which mode ran

Every response carries the mode the request was handled in.

```bash
curl -s -D- -o /dev/null http://127.0.0.1:8787/v1/messages \
  -H "x-api-key: dummy-not-a-key" \
  -H "anthropic-version: 2023-06-01" \
  -H "content-type: application/json" \
  -d '{"model":"claude-sonnet-4-5","max_tokens":16,"messages":[{"role":"user","content":"hi"}]}'
```

```text
X-Cave-Mode: compress
X-Cave-Optimization: none
X-Cave-Project: local
X-Cave-Request-Id: 01a0ac85-a39c-7861-9646-48f46aeb38f5
X-Cave-Trace-Id: 49e269ad49c2525f9ece50954192080b
```

The `x-cave-` lines from a real response, with the provider's own headers dropped. The key in that run was
deliberately invalid, so Anthropic answered 401 and nothing was billed: the proxy stamps these headers either
way. `x-cave-optimization`
lists the optimizer ids that ran, or `none`. When compression actually removed bytes, four more headers
appear: `x-caveman-compression-ratio`, `x-caveman-recovery-handle`, `x-caveman-tokens-before` and
`x-caveman-tokens-after`, with `x-caveman-token-count-basis: estimated_engine_o200k`.

The listener reports the same thing without a request:

```bash
~/.caveman/bin/caveman-proxy status
```

```json
{
  "owner": "start",
  "mode": "record",
  "instance_token": "…",
  "pid": 4603,
  "port": 8787,
  "started_at": "…",
  "version": "dev",
  "recovery_via_mcp": false,
  "compat_upstreams": {
    "opencode-go": "https://opencode.ai/zen/go"
  },
  "provider_upstreams": {
    "anthropic": "https://api.anthropic.com",
    "gemini": "https://generativelanguage.googleapis.com",
    "openai": "https://api.openai.com"
  },
  "compat_forward_headers": {
    "opencode-go": null
  }
}
```

Captured from caveman-proxy bin-v1.1.7, with `instance_token` and `started_at` replaced by `…`. The token
identifies one run of the listener. `owner` says which door started this proxy, `start` or `wrap`. The two
upstream maps are what this listener resolved at startup, so they show the configuration the running process
is actually using.
