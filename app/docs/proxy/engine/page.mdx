The engine is the Go component that makes a payload smaller: it detects what kind of content the bytes
are, routes them to the compressor for that type, writes the original to a content-addressed store, and
returns the smaller view plus the handle that gets the original back. The [proxy](/docs/proxy) calls it on
every eligible request, and it also ships as `caveman-engine`, a binary that reads stdin and writes stdout.

Here to turn compression on rather than to read the algorithm? [Wrap an agent](/docs/proxy/wrap) is one
command and this page is not on the path.

## One payload, end to end

`orders.json` is a 40 element JSON array, one order per line, 5,515 bytes.

```bash
curl -O https://docs.caveman.so/examples/engine/orders.json
head -3 orders.json
```

```json
[
  {"order_id": "ORD-1001", "customer": "cust_001", "status": "fulfilled", "total_cents": 1237, "currency": "USD", "region": "eu-west-1"},
  {"order_id": "ORD-1002", "customer": "cust_002", "status": "fulfilled", "total_cents": 1274, "currency": "USD", "region": "eu-west-1"},
```

```bash
caveman-engine compress < orders.json > smaller.json 2> report.json
cat smaller.json
```

## The pipeline

`Compress` runs the same seven steps every time, in this order.

<Steps>
<div>
**Unwrap presentation.** A `<file name="…">` wrapper and a read tool's line-number gutter (`1\t{`,
`2\t  "unit"`) are stripped before anything else looks at the bytes, then restored afterwards. Left in
place they make JSON fail `json.Valid` and source fail to parse, so everything would route to `text`.
</div>

<div>
**Detect the content type,** unless the caller forced one with `--type`. Detection reads bytes only. See
[All compressors](/docs/proxy/compressors#how-detection-decides) for the signals and their order.
</div>

<div>
**Count the input** with the embedded `o200k_base` tokenizer. That number is `tokens_before` and it is the
denominator of every ratio on the page. See [Token counting](/docs/proxy/tokens).
</div>

<div>
**Look up the compressor** for that content type. No compressor registered for the type means the original
bytes are returned with `ratio: 0` and no handle.
</div>

<div>
**Check the safety class.** Every compressor declares a class on the S0 to S4 ladder below. S4 carries
`RequiresCCR`, so it may only run when the original can be stored first. With no store and no
caller-supplied recovery, the original is returned unchanged, and an unrecognised class is treated the same
way.
</div>

<div>
**Run the compressor and count the output.** Dispatch goes to the compressor's `CompressWithMetadata` when
it has one, otherwise to `CompressQuery` when `Options.Query` is set and the compressor is query aware,
otherwise to plain `Compress`. The result is re-wrapped in whatever presentation step 1 stripped and
counted after that, so both sides of the ratio are the bytes as they cross the boundary. A parse problem
returns `ok=false` and the original goes through. So does output that counts the same or more tokens than
the input, and output that is byte-identical to the input.
</div>

<div>
**Store the original, then publish.** For an S4 result the original bytes go to the recovery store first,
as a row holding the content type, the compressor, both token counts, the original bytes and the
compressor's recovery metadata. Only after that write succeeds does the call set `Output`, `TokensAfter`,
`Ratio`, `Method` and `RecoveryHandle`, so a caller never holds transformed bytes whose original was not
saved. `Method` defaults to the content type and `lossless_to_model` to the safety class's own
reversibility when the compressor states neither.
</div>
</Steps>

Step 5's ladder has five rungs. Every compressor in this build declares S4.

| Class | What it changes | Store first |
|---|---|---|
| S0 | Metadata and accounting. Model-visible bytes stay identical. | no |
| S1 | Provider-native hints such as cache markers and routing. Model-visible bytes stay identical. | no |
| S2 | Structural changes that need SDK cooperation. | no |
| S3 | Behavioural changes such as routing and reasoning effort. | no |
| S4 | Lossy structural compression. Model-visible bytes change. | yes |

Four fields on `Options` steer that run.

| Option | What it does |
|---|---|
| `Mode` | `record` is the default and returns the input byte-identical, skipping steps 4 to 7. `compress` runs them. Any unrecognised string resolves to `record`. See [Modes](/docs/proxy/modes). |
| `Type` | Forces a content type and skips detection. Empty means detect. |
| `Query` | Biases a query-aware compressor toward the items a query ranks, by BM25 over the payload's own units. A compressor without that path ignores it. |
| `ExternalRecovery` | Lets a gateway that already stored the original outside the CCR store run a lossy compressor with no store attached. The caller has to have written the original before it forwards the compressed bytes. |

## What Compress returns

| Field | Meaning |
|---|---|
| `Output` | The compressed bytes, or the input bytes unchanged on pass-through. Not serialised into the JSON report. |
| `content_type` | The detected type, or the one `--type` forced. |
| `tokens_before` / `tokens_after` | Local counts of input and output. Equal on pass-through. |
| `token_count_basis` | The counter that produced both numbers, `o200k_base` by default. |
| `ratio` | `(before - after) / before`, between 0 and 1. Zero on pass-through. |
| `basis` | Always `inferred`. There is no configuration that changes it. |
| `recovery_handle` | The CCR handle for the original. Absent on pass-through. See [Recovery](/docs/proxy/recoverable). |
| `method` | The concrete transform a compressor chose, such as `elision` or `toon`. Defaults to the content type. |
| `lossless_to_model` | Whether the model-visible output kept the full value. `false` for an elision, `true` for a re-encoding such as TOON. |

`PassedThrough()` is true when the handle is empty, the method is empty and the ratio is zero, which is the
one combination the pass-through paths produce.

## Limits

  ["Store", <>512 MiB of retained payloads, set by <code key="m">CAVEMAN_CCR_MAX_BYTES</code> as a positive byte count read at startup.</>],

The two store failures differ. A store the binary cannot open stops the run: `caveman-engine` exits 1 with
`cannot open recovery store: …` on stderr and writes nothing to stdout. A store it opened but cannot write
to is a pass-through: the original bytes go to stdout, `ratio` is 0, and the report carries
`"error": "cave_ccr_unavailable"`.

Code compression depends on how the binary was built. With cgo it uses tree-sitter and handles Go, Python,
Rust, Java, C, C++, and JavaScript or TypeScript (the TypeScript grammar parses both). Without cgo, and in
the WASM build, it uses the Go standard library parser and handles Go, leaving other languages untouched
rather than mangling them.

## Reference

### The binary

```bash
caveman-engine compress [--type <content-type>] < input   # payload to stdout, report to stderr
caveman-engine detect < input                             # one word: the content type
caveman-engine retrieve <handle> [query]                  # the original bytes, or the parts a query ranks
caveman-engine stats                                      # totals and per-type totals from the store
caveman-engine registry                                   # the transform capability manifest as JSON
caveman-engine toon encode | decode                       # stateless JSON to TOON and back
caveman-engine pixel render | simulate                    # see Pixel mode
caveman-engine evals run [--fixtures DIR]                 # the committed fixture set
```

`--type auto` is the same as omitting the flag. `--type` is also how you reach the five transforms that
detection never selects on its own: `toolschema`, `toolschema-annotations`, `toon`, `a11y` and `repetition`.
One of them, `toolschema-annotations`, is held out of the manifest on purpose, so `registry` prints one id
fewer than the set of transforms you can force.

Build it from the product repository:

```bash
git clone https://github.com/JuliusBrussee/caveman
cd caveman && go build -o ./bin/caveman-engine ./engine/cmd/caveman-engine
```

### Who calls it

The same four call surface, `Compress`, `Retrieve`, `Detect` and `Stats`, backs every product that
compresses anything.

| Caller | How it uses the engine |
|---|---|
| [Proxy](/docs/proxy) | Links it as a library and compresses the live zone of each provider request, the part the provider has not cached. Everything below it is the frozen prefix. See [Prompt caching](/docs/proxy/caching). |
| [MCP server](/docs/mcp) | Exposes `caveman_compress`, `caveman_retrieve` and `caveman_stats` as tools. |
| [cavemem](/docs/memory) | Compresses stored memories and packs recall results into a token budget. |
| [caveman-shrink](/docs/shrink) | Compresses command output and tool catalogs at the shell. |
| [caveman-browse](/docs/browse) | Compresses a page's accessibility tree before the agent reads it. |
| WASM build | `cavemanCompress`, `cavemanDetect` and `cavemanRetrieve` in a browser, over an in-memory store. |

### Simulate and Retrieve

`Simulate` runs the identical detect, route, compress and count sequence and stores nothing. It reports the
reduction a real `Compress` would achieve, plus `recoverable`, which is false when a lossy compressor
matched but no store is configured. It is a Go API with no CLI verb behind it. The closest surface a
command line reaches is the proxy in `record` mode with `CAVEMAN_OBSERVE_ESTIMATE` set, which measures what
compression would have removed on copies of each live-zone segment while the forwarded bytes stay identical.

`Retrieve` resolves two id spaces. A handle that misses the blob table is looked up again in the typed
object table the native runtime's tool-output masking mints, and only then fails, so a reference an agent
was handed never resolves to another dead pointer.
