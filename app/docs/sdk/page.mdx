Three doors add Caveman to an application you already run, in order of how much code changes: swap a base URL in the provider SDK you already import, wrap one framework call with middleware, or call the client library directly. All three talk to a Caveman service over HTTP; the compression happens there, not in your process.

Running an agent in a terminal rather than an application? Use [Wrap an agent](/docs/proxy/wrap).

## Door one: swap the base URL

`caveman snippets` prints the recipe for the SDK you already use, filled in with your proxy address and an app label. This is the OpenAI TypeScript recipe from `integrations/recipes/openai-ts.json`, rendered against a local proxy, as printed by `caveman snippets`:

```bash
caveman snippets openai-ts --app my-service
```

```ts
// One constructor argument. /w/my-service in the base URL attributes this app's spend — no custom headers.
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "http://localhost:8787/w/my-service/openai/v1",
  apiKey: process.env.OPENAI_API_KEY,
});

// Chat Completions and the Responses API both route through the gateway.
const res = await client.responses.create({
  model: "gpt-5.5",
  input: "Why is the sky blue?",
});

// Connected to Caveman Cloud? Add gateway auth + BYOK headers:
//   defaultHeaders: { "x-cave-api-key": CAVE_API_KEY, "x-cave-upstream-key": OPENAI_API_KEY }
```

`caveman snippets` with no argument lists the twelve recipes. The routes behind them are on [Providers and base URLs](/docs/proxy/providers).

## Door two: wrap the framework call

Middleware swaps eligible tool results for a shorter copy on the way out and adds a `caveman_retrieve` tool so the model can read the original back. The call site keeps its shape:

```diff
-const result = streamText(options);
+const result = streamText(withCaveman(options, { runtime, scope }));
```

`runtime` is a `MiddlewareRuntime` pointed at the local proxy, `scope` identifies the conversation. [Middleware](/docs/sdk/middleware) has the whole procedure and the report it prints for every call.

## Door three: the client library

`@caveman-ai/sdk` and `caveman-sdk` are thin HTTP clients. They forward provider calls and compression calls to a Caveman service and map the response; they hold no compressor of their own.

```ts
import { Cave } from "@caveman-ai/sdk";

const cave = new Cave({ apiKey: process.env.CAVE_API_KEY, baseURL: process.env.CAVE_BASE_URL, agent: "support-agent" });
const report = await cave.compress(logText);
console.log(report.tokensBefore, report.tokensAfter, report.ratio);
```

The `/sdk/v1/*` routes this uses are served by a Caveman service, not by the local proxy on 127.0.0.1:8787. Against an endpoint that does not serve them, `compress()` returns the input unchanged with `ratio: 0`.

That service is Caveman Cloud, which is in private development with a waitlist at [caveman.so](https://caveman.so). [Caveman Cloud](/docs/cloud) has what is known today. The other two doors need only the local proxy.

## The three doors

| Door | What changes | What you need running |
|---|---|---|
| Base URL swap | One constructor argument | The local proxy, `caveman start` |
| Middleware | One wrapper around an existing call | The local proxy, `caveman start` |
| Client library | New calls you write | Caveman Cloud, which is in private development. It serves the `/sdk/v1/*` routes; the local proxy does not |
