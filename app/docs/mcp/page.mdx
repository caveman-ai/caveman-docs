`caveman-mcp` serves five compression tools over stdio to any MCP client: compress a payload, recover the original bytes, read this process's totals, and encode or decode TOON. It links the [compression engine](/docs/proxy/engine) in-process, opens no network connection, and labels every figure `inferred`.

`caveman claude` already registers this server in Claude Code's own config, and so does `caveman <agent>` for Codex, Gemini CLI, Hermes and opencode. A one-session `caveman wrap` gives Claude Code and Codex a temporary copy. Every other agent, and any client caveman does not wrap, is what this page is for. [Wrap an agent](/docs/proxy/wrap#recovery-has-to-be-installed) has the per-agent table.

## Configure a client

```json
{
  "mcpServers": {
    "caveman": { "command": "npx", "args": ["-y", "caveman-mcp"] }
  }
}
```

That goes in `.mcp.json` for Claude Code, and in the equivalent block for Codex. The npm launcher is MIT: on first run it downloads the matching binary, verifies a key-signed checksum manifest and the artifact's SHA-256, and caches it under `~/.caveman/bin`. No Go toolchain and no global install are needed.

To point at a binary you already reviewed:

```bash
CAVEMAN_MCP_BIN=/path/to/caveman-mcp npx caveman-mcp
```

Or let the CLI write the registration:

```bash
caveman mcp install claude
```

With no agent named it installs for every known agent found on `PATH`. `caveman mcp uninstall` removes the registration and the ownership marker again. `--server caveman-browse`, `--server caveman-cloud` and `--server caveman-delegate` register the other three servers through the same verb.

## The five tools

| Tool | Input | Returns |
|---|---|---|
| `caveman_compress` | `input`, and optionally `content_type` (alias `type`) | `compressed`, `ratio`, `tokens_before`, `tokens_after`, `basis`, `content_type`, `recovery_handle` |
| `caveman_retrieve` | `recovery_handle`, and optionally `query` | The byte-exact original with no query; ranked complete records with one |
| `caveman_stats` | Nothing | `tokens_before`, `tokens_after`, `requests`, `ratio`, `basis`, `scope` |
| `caveman_toon_encode` | `input`, a JSON string | The TOON encoding with both sizes, or the input unchanged with a note |
| `caveman_toon_decode` | `input`, a TOON string | The decoded JSON, or an error |

`ratio` is 1 minus `tokens_after` divided by `tokens_before`, so 0.98 means the payload came out at 2 percent of its counted size.

## Call one

Two JSON-RPC lines piped into the binary, an `initialize` and a `tools/call`:

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"docs","version":"1"}}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
  | ~/.caveman/bin/caveman-mcp
```

```json
{"jsonrpc":"2.0","id":1,"result":{"capabilities":{"tools":{}},"protocolVersion":"2024-11-05","serverInfo":{"name":"caveman","version":"dev"}}}
```

One real run. The `tools/list` reply follows on the next line and carries all five tool definitions with their JSON Schemas.

A `tools/call` for `caveman_compress` returns one text content block. Its body is a JSON object. Compressing a 902-line service log, 92,799 bytes, where one request in the middle timed out:

```json
{
  "ratio": 0.9897139399643685,
  "tokens_before": 29749,
  "tokens_after": 306,
  "basis": "inferred",
  "content_type": "log",
  "recovery_handle": "ccr_9b083ac0963692270dca7b1c469961d7",
  "method": "log",
  "lossless_to_model": false
}
```

The `compressed` field is elided from that block for length. It reads like this:

The error, its two stack frames and the lines that bracket the file survive. Each elision marker states what was true of every line it replaced, so a question about the shape of the dropped traffic is answerable without a retrieval call.

<Note title="ratio 0 means the original came back, not that a call failed">
Input the engine cannot make smaller, or cannot store the original for, is returned unchanged with `ratio` at 0 and `recovery_handle` at `null`. That is a success, not an error. A run where the recovery store is unavailable looks identical, so check that `~/.caveman/ccr.db` is writable before concluding a payload is incompressible.
</Note>

## Recovery

Compression is lossy and reversible. The original bytes are written under the handle before the smaller view is emitted, so the handle is valid the moment you have it. `caveman_retrieve` with the handle and no query returns those bytes exactly:

```bash
~/.caveman/bin/caveman-engine retrieve ccr_9b083ac0963692270dca7b1c469961d7 | wc -lc
```

```text
     902   92799
```

The same 902 lines and 92,799 bytes that went in.

Pass a `query` and retrieval returns complete records ranked against it, never a plucked line. Wherever it skipped content it prints `… [caveman: non-adjacent] …`, including at the start and the end. Records on either side of that marker are not consecutive, so nothing may be read into their order or into the gap.

An unknown handle is an explicit error with a `cave_` code, not an empty result. Handles are normalized on the way in: a bare `ccr_…`, a full `<<ccr:…>>` marker and a `ccr:ccr_` prefix all resolve.

Retrieval is exempt from the server's result-size cap, so an original larger than the cap still comes back whole. Repeated calls keep working after the host compacts its transcript.

## Stats

`caveman_stats` counts only what this server process handled, including repeated inputs and pass-throughs, and `scope` says `session` to make that explicit. It excludes other processes and earlier sessions, and it is never a `verified` figure. For everything the proxy recorded across sessions, use `caveman stats` from [the CLI](/docs/cli#inspect).

## Limits

The five tools cost tool-schema tokens on every request that carries them, which is the trade for having recovery available to the model at all. [Numbers and limits](/docs/counting) has the accounting and the meaning of `inferred`; [Recovery](/docs/proxy/recoverable) covers the store behind the handles.
