An eval is a fixture plus the graders that decide whether an answer to it was acceptable. A build runs every declared eval against candidate plans, and writes `.caveman/agent.lock.json` only when one candidate clears the quality floor and the guardrails; anything else ends with a status and no lock. `runLocked()` then executes that frozen plan.

```ts
import { eval as defineEval } from "@caveman-ai/agent";
import { readFileSync } from "node:fs";

export const refundRequest = defineEval({
  id: "refund-request",
  lineageId: "refund-family",
  split: "profile",
  input: readFileSync(new URL("../tickets/refund-request.md", import.meta.url), "utf8"),
  quality: [
    { type: "tool_called", tools: ["lookup_order"] },
    { type: "contains", fragments: ["eligible"] },
    { type: "not_contains", fragments: ["refund issued", "refund completed"] },
  ],
});
```

Name each fixture file with a literal `new URL(…, import.meta.url)`. A computed path is not lockable, so the source graph cannot pin its bytes and the build refuses it.

## Fixture fields

| Field | What it declares |
|---|---|
| `id` | Required, non-empty. |
| `lineageId` | The task family. Split isolation uses it so a holdout cannot share a family with a fixture the search tuned on. |
| `split` | `profile`, `development` or `holdout`. A v3 build requires every fixture to declare one, and never invents a split. |
| `input` | What the agent is run on: the `AgentInput` for this task. |
| `tools` | `{ mode: "fixture" }` by default. `{ mode: "live", sandbox }` runs real tools and requires an explicit sandbox. |
| `quality` | At least one grader. The compiler admits the ones it can lower without a model or a network: `contains`, `not_contains`, `tool_called`, `exact_match`, `json_schema`. |
| `guardrails` | `{ type: "latency_threshold", p95_ms }` and `{ type: "error_rate", max }`. |

Graders come from `@caveman-ai/evals` and are ordinary functions, so you can run one against a finished run before you ever start a build. `@caveman-ai/evals` is not published, and a path install of `@caveman-ai/agent` does not pull it in, so install it from the same checkout you [built the agent package from](/docs/agent-sdk/install#build-from-the-checkout):

```bash
npm install <checkout>/packages/evals
```

```ts
import { agent, run, schema, tool } from "@caveman-ai/agent";
import { fauxModel, scriptedStream } from "@caveman-ai/agent/testing";
import { grade } from "@caveman-ai/evals";

const lookupOrder = tool({
  name: "lookup_order",
  description: "Look up an order by id.",
  effect: "read",
  input: schema.object({ orderId: schema.string() }),
  execute: async ({ orderId }) => ({ orderId, status: "delivered" }),
});

const desk = agent({
  id: "support-desk",
  instructions: "Decide the refund from the order record.",
  model: fauxModel({ priced: true }),
  tools: [lookupOrder],
  sandbox: "host",
});

const result = await run(desk, "Refund for NB-1042?", {
  streamFn: scriptedStream([
    { toolCalls: [{ name: "lookup_order", args: { orderId: "NB-1042" } }] },
    { text: "NB-1042 is eligible for a refund." },
  ]),
});

console.log(await grade({ type: "contains", fragments: ["eligible"] }, result.text));
console.log(await grade({ type: "not_contains", fragments: ["refund issued"] }, result.text));
console.log(await grade({ type: "tool_called", tools: ["lookup_order"] }, result.toolCalls));
```

```text
{ passed: true, reason: 'all fragments present' }
{ passed: true, reason: 'no forbidden fragments present' }
{ passed: true, reason: 'all required tools called' }
```

Captured from that file at source 0.1.0 of `@caveman-ai/evals`. The value each grader reads differs: the text graders take the answer, and `tool_called` takes something carrying tool calls, which `result.toolCalls` is because it is the tool names in call order. `exact_match` compares trimmed and case-insensitively by default; `case_sensitive` and `remove_punctuation` opt into stricter variants.

## The build config

```ts
import { defineBuild } from "@caveman-ai/agent/build";

export default defineBuild({
  entry: "./agent.ts",
  evals: "evals/*.eval.ts",
  maxSearchCostUsd: 2,
});
```

| Field | Default | What it sets |
|---|---|---|
| `entry` | required | The definition module, or `"."` for an [agent directory](/docs/agent-sdk/define#load-an-agent-directory). |
| `evals` | required | Glob for the eval modules. |
| `requiredFixturePassRate` | `1` | Share of fixtures a candidate must pass. |
| `qualityRetention` | `0.98` | Quality floor against the baseline, judged on a 95 percent lower confidence bound. |
| `maxSearchCostUsd` | `2` | Ceiling on what the candidate search may spend. |
| `efficiency`, `lock`, `sandbox` | `"max"`, `"strict"`, `"required"` | Fixed values. Any other value is refused. |
| `allowedModels`, `deniedModels`, `maxP95LatencyMs`, `forbiddenSafetyClasses` | unset | Extra admission policy. |

An unknown key throws, and `dataResidency` throws outright rather than being accepted and ignored.

## Run it

```bash
npx caveman-agent build caveman.config.ts
npx caveman-agent check caveman.config.ts
```

`build` compiles, searches candidates, runs the evals and writes the lock. `check` re-derives the current digests and compares them against the lock without spending anything:

```text
caveman-agent: cave_build_lock_missing: add eval fixtures, then run npm run build
```

Captured from `check` in a hand-written project that has a config and evals but no lock yet. An `entry: "."` project written by the initializer fails both commands at commit `311be40` with `caveman-agent: EISDIR: illegal operation on a directory, read`, because the source graph walker tries to read the directory URLs in the generated `run.ts` as source files. Point `entry` at a module until that is fixed. When a lock is present and current, `check` prints its build digest, the selected plan, the catalog cost per task, and the line `local evidence: passed (estimate only)`. A lock whose inputs moved fails with `cave_stale_lock:` and the list of what changed, drawn from the source graph, the agent definition, the Context IR, the eval suite, the framework version, the harness versions, the transform registry and the price catalog.

## Why a failed eval cannot produce a lock

`compile()` returns a status and a lock, and the lock is present in exactly one case.

| Status | What happened | Lock |
|---|---|---|
| `locked` | A candidate passed every fixture and guardrail. | written |
| `needs_eval` | No eval fixture was declared. | none |
| `no_passing_build` | Every complete candidate missed the quality floor or a guardrail. | none |
| `incomplete_evidence` | The evidence set was not complete for the baseline or a candidate. | none |
| `search_budget_exceeded` | The search hit `maxSearchCostUsd` first. | none |

`compileAndWrite()` returns early when the result carries no lock, so the file on disk is never touched by a build that did not pass. The lock itself is written to a temp file with `wx` and then renamed, so a half-written lock cannot appear either. An agent whose sandbox posture is `host` anywhere in its graph is refused before any of this with `cave_host_sandbox_lock_ineligible`.

## What a lock contains

`schema_version`, the agent id, and digests for the build policy, the selected plan, the source graph, the agent definition, the Context IR and the eval suite. Then the harness and its versions, the framework version, the transform registry and external provenance digests, the price catalog digest, the baseline and selected plan ids, the plan itself, and the evidence: `quality_retention_lcb95`, `error_rate`, `p95_latency_ms`, `catalog_cost_usd_per_task` and `completed_runs`, with `basis: "inferred"`.

`runLocked` re-checks the lock against the definition digest, the framework version, the catalog digest and the engine's transform registry before the first call, and refuses on any mismatch with its own code. That is the same evidence `check` uses, applied at the point where spending is about to start. [Running a locked build](/docs/agent-sdk/run#running-a-locked-build) has the call.

## Limits

Everything a build measures is a local estimate labelled `inferred`, over the fixtures you wrote, on the machine that ran it. `catalog_cost_usd_per_task` is a public-catalog price for the fixture set, not a bill and not a projection. [Numbers and limits](/docs/counting) has the rules those words follow.
