The model router sends each call to the cheapest model in your pool that passes your evals, and leaves the traffic where it is when nothing does. It runs inside the [Caveman Cloud](/docs/cloud) request path, on requests that ask for it by naming `cave-auto` as the model. Cloud is in private development; the waitlist is at [caveman.so](https://caveman.so).

## What the decision weighs

Task complexity is one input. The rest are what a router reading only the prompt gets wrong:

- **Cache and session state.** Moving a live conversation to another model throws away warm cached context. A candidate's lower per-call price has to beat the cost of rebuilding it.
- **Tool and output requirements.** Function calls, structured output, vision and API compatibility are eligibility checks. A model that cannot satisfy the request is excluded before price is compared.
- **Context and capacity.** Input plus reserved output has to fit the candidate's context window, and the candidate has to sit inside your project's allowed pool.
- **Quality evidence.** Your evals set the bar. Where the evidence for a candidate is missing, the router holds the baseline rather than guessing.

## How a route reaches traffic

Record, then replay against fixtures, then shadow, then canary, then active. A quality regression rolls the change back automatically, so the eligibility rules are enforced by the system rather than by a spreadsheet.

## The published number

39.6 percent lower spend on replayed-traffic benchmarks, modelled at list prices. Carry that basis every time the figure moves: replayed traffic priced against a public catalog, not a customer invoice. On your own traffic a router figure starts as `inferred` and stays there until a provider bill shows the change. [Numbers and limits](/docs/counting#vocabulary) defines those words.
