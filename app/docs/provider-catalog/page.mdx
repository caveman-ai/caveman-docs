The provider catalog is a YAML table of published token prices and model capabilities, one row per provider, model and region. It is data and a JSON Schema, with no runtime code, and it is Apache-2.0 so you can read it, vendor it, or check a price against it. It lives at `shared/provider-catalog/` in the product repository.

Looking for what a local run cost you? Local tools count tokens and stop. [Numbers and limits](/docs/counting) explains why.

## One row

This is the committed entry for `claude-opus-4-8`, copied whole from `catalog/current.yaml`:

```yaml
- provider: anthropic
  model: claude-opus-4-8
  region: global
  currency: USD
  pricing:
    input_per_million: 5.00
    output_per_million: 25.00
    cache_read_input_per_million: 0.50
    cache_write_input_per_million: 6.25
    cache_write_1h_input_per_million: 10.00
    reasoning_output_per_million: null
    batch_discount_fraction: 0.50
  capabilities:
    messages_api: true
    effort_levels: [low, medium, high, xhigh, max]
    count_tokens: true
    prompt_cache: true
    streaming: true
    message_batches: true
    context_editing: true
    inference_geo_us_multiplier: 1.10
    context_window_tokens: 1000000
    tools: true
    vision: true
    json_mode: true
  sources:
    - https://platform.claude.com/docs/en/about-claude/pricing
    - https://platform.claude.com/docs/en/about-claude/models/overview
    - https://platform.claude.com/docs/en/build-with-claude/effort
  verified_at: 2026-08-10T00:00:00Z
  capabilities_verified_at: 2026-08-10T00:00:00Z
```

A row can also carry a YAML comment above `pricing` recording a dated changeover the drift detector must roll forward. `claude-sonnet-5` has one today.

`current.yaml` today holds 50 rows: 10 OpenAI, 9 Anthropic, 2 Gemini, 25 Bedrock and 4 Vertex. Regions are provider regions, with `global` for rows that price the same everywhere.

## Reading a price

Every rate is per million tokens in the row's `currency`. The name says which side of the call it covers.

| Field | What it prices |
|---|---|
| `input_per_million` | Tokens the model read. |
| `output_per_million` | Tokens the model wrote. |
| `cache_read_input_per_million` | Input tokens served from the provider's prompt cache. |
| `cache_write_input_per_million` | Input tokens written into that cache. |
| `cache_write_1h_input_per_million` | The same, at a longer cache lifetime, where the provider sells one. |
| `reasoning_output_per_million` | Reasoning tokens, when the provider bills them separately from output. |
| `batch_discount_fraction` | A discount, not a multiplier. `0.50` means half off. |
| `long_context_threshold_tokens` and its two multipliers | The point at which a provider switches to long-context rates, and what it multiplies input and output by past it. |

A field that does not apply to a model is written as explicit `null` rather than left out, so a missing rate is a stated absence rather than an oversight.

Three keys inside `capabilities` are price wearing a capability's clothes: `regional_processing_multiplier` and `inference_geo_us_multiplier` multiply the row's token rates, and `region_agnostic_pricing` decides whether a `global` row can answer a lookup for a specific region at all. Editing one of them is a price edit.

## Two dates that mean different things

`verified_at` is the date this row's **pricing** was last checked against the vendor's published pricing page. It is the only input to the catalog version stamped on cost reports, so it moves only when someone re-checks prices.

`capabilities_verified_at` is the date the capability data this row **asserts** was last checked against the vendor's model docs. Nothing money-related reads it. A key whose value is explicit `null` asserts nothing, so it sits outside what that date covers.

Every current row must match the immutable dated snapshot its `verified_at` names, on the pricing-relevant columns. That is why a snapshot named by any current row is never deleted, and why a row whose price actually changed gets a new date and a new snapshot rather than reusing an old one.

## How stats uses it

`caveman stats` reports token counts always and a price only when it can stand behind one. The proxy records a request's tokens from its own offline counter and labels them `inferred`. To attach a price it needs all of: provider-reported usage that is complete enough to price, an exact catalog match for the provider and model and region, and a catalog version that is not the `unpriced:` form.

When any of those is missing, the row keeps its token counts and the savings basis says why: `unpriced` for no price, `usage_incomplete` for usage the provider did not fully report, `counterfactual_tier_unknown` when a smaller payload might have crossed a pricing tier the local counter cannot prove. Subscription-authenticated sessions stay tokens-only regardless, with no dollar figure at all.

That is the catalog's whole job here: it is the table a hosted comparison reads, and it is why the local tools can decline to guess instead of averaging something plausible.

## Unknown is not false

`tools`, `vision` and `json_mode` are explicitly nullable. A row writes `null` when the vendor's own docs do not state the answer, with a comment naming what was checked. Twenty Bedrock rows carry `null` for exactly this reason. A guessed `true` would route traffic to a model that may not support the feature, and a guessed `false` would delete a candidate that does.

Withdrawing a claim is not a verification. Replacing an unverified value with `null` removes an assertion rather than checking one, so the capability date stays where it was.

## Validate a change

```bash
python shared/provider-catalog/validate_catalog.py
```

```
provider catalog valid: current rows are fresh, sourced, and snapshot-backed
```

The schema is `schemas/provider-catalog.schema.json`, JSON Schema draft 2020-12. Unknown YAML fields, duplicate provider and model and region rows, invalid URLs or timestamps, and unsafe prices all reject the file rather than loading partially. The `package.json` scripts in that directory only parse the schema itself, so run the validator for the catalog data.
