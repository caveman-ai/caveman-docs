The engine ships a committed fixture set and a grader harness that replays it. Each fixture is compressed, then judged: did the ratio land in its band, is the output still parseable, did the values an answer depends on survive, and can the original bytes be fetched back. A grader type the harness does not recognise counts as a failure, so a misspelling in a manifest can never read as a pass.

## Run it

No account, no API key, no provider call. It reads fixtures embedded in the binary.

```bash
caveman-engine evals run
```

Two JSON documents come back on stdout, one after the other.

The first is the corpus report: a roll-up of `passed`, token and word totals and a probe tally, plus a `fixtures` array holding one object per fixture. [Where a number comes from](/docs/counting#where-a-number-comes-from) shows the roll-up. One element of the array looks like this:

```json
{
  "name": "json-smartcrusher",
  "content_type": "json",
  "tokens_before": 1671,
  "tokens_after": 264,
  "ratio": 0.8420107719928187,
  "basis": "inferred",
  "passed": true,
  "byte_recoverable": true
}
```

The second document is the pixel density gate, which checks the image renderer rather than a fixture. It carries `passed` and a `pixel_density_gate` array of named checks, eighteen of them in this run, each with its own `passed` and a `detail` string:

```json
{
  "name": "capacity balanced",
  "passed": true,
  "detail": "chars/page=46291 want configured balanced capacity"
}
```

Captured from one local run at binary release `bin-v1.1.0`, trimmed to the fields under discussion. `caveman setup --install` today fetches `bin-v1.1.7` (`packages/cli/src/binaries.generated.ts`), so counts and ratios may move. `caveman evals run` through the CLI does the same thing, and `--fixtures <dir>` points the harness at a manifest of your own.

Seventeen fixtures ran in that report, covering JSON, HTML, logs, repeated lines, CSV, YAML, Go, Python, TypeScript, tool catalogs, TOON, plain text and terminal sessions. Three of them are pass-through cases, which exist to check that content the engine should leave alone comes out byte-identical with a ratio of zero.

## What a grader checks

A fixture names its graders in the manifest. Every one of them must pass.

| Grader | What it asserts |
|---|---|
| `ratio_threshold` | The realised ratio sits inside `[min, max]`. A band, not a floor, so a suspiciously large cut fails too. |
| `compressed` | The output is smaller than the input. |
| `byte_identical` | The output equals the input, for fixtures that must pass through untouched. |
| `valid_json` | The output parses as JSON. |
| `json_or_toon_round_trip` | The output is valid JSON, or it is TOON that decodes back to the original structure. |
| `json_schema` | The output satisfies a JSON schema given in the manifest. |
| `contains`, `not_contains` | A literal string survived, or was removed. |
| `exact_match` | The output equals an expected value after trimming. |
| `recall_keys` | Every named value is still present, at a minimum recall the manifest sets. This is what catches a compressor that keeps the head and tail of an array and drops the interesting row in the middle. |
| `tool_sequence` | The tool calls in the output appear in the expected order. |
| `toon_round_trip` | TOON output decodes back to the input structure. |

Anything else is a failure with the reason recorded. That is the rule the harness exists to enforce: an unknown grader never silently passes.

## Retention probes

A grader reads the output. A probe asks a narrower question: is this one critical value still visible to the model, or at least recoverable byte for byte? Each probe carries a dimension, and the report tallies them per dimension.

```json
{
  "by_dimension": {
    "error": { "total": 4, "retained": 4, "recoverable": 0, "lost": 0 },
    "identifier": { "total": 2, "retained": 2, "recoverable": 0, "lost": 0 },
    "number": { "total": 3, "retained": 2, "recoverable": 1, "lost": 0 },
    "path": { "total": 1, "retained": 1, "recoverable": 0, "lost": 0 },
    "status": { "total": 2, "retained": 2, "recoverable": 0, "lost": 0 }
  }
}
```

Three states, in descending order of comfort. `retained` means the value is in the compressed output. `recoverable` means it was removed but the original is behind a handle. `lost` means neither, which fails the fixture. In the run above one number moved from retained to recoverable and none were lost.

Reports carry the SHA-256 of each probed value rather than the value itself, so a published report never leaks the answers of a hidden fixture suite.

## Writing a fixture

A manifest entry is a file plus its graders. This is the committed `json-smartcrusher` entry in full, from `engine/evals/fixtures/manifest.yaml`:

```yaml
  - name: json-smartcrusher
    file: json_smartcrusher.json
    query: "What error code appears in the results"
    probes:
      - {dimension: error, value: "ERROR-503"}
      - {dimension: number, value: '"id": 20'}
    quality_task:
      question: "What error code appears in the results?"
      graders:
        - {type: exact_match, value: "ERROR-503"}
    graders:
      - {type: json_or_toon_round_trip}
      - {type: compressed}
      - {type: ratio_threshold, min: 0.60, max: 0.95}
      - {type: contains, value: "ERROR-503"}
      - {type: contains, value: "__caveman_elided__"}
      # The error and the anomaly sit in the MIDDLE of the array, where naive
      # head/tail sampling would drop them — recall_keys checks they survive.
      - {type: recall_keys, options: {must_contain: ["ERROR-503", "timeout", "9999"], min_recall: 1.0}}
```

`type` forces a content type instead of letting detection choose. `mode` selects `compress` or `record`. `query` is passed to the compressors that rank by relevance. The `quality_task` is a question with an expected answer, graded when the harness is given a model runner; the command above has none, so the structural graders and the probes run on their own.

## The skill's own eval

A separate harness, at [`evals/`](https://github.com/JuliusBrussee/caveman/blob/main/evals/README.md) in the product repository, measures the skill rather than the engine. It runs a fixed list of developer questions through Claude Code under three conditions: no system prompt, `Answer concisely.`, and `Answer concisely.` plus the skill body. The honest delta is the skill against the terse control, because comparing against the bare baseline credits the skill with the generic ask to be brief.

```bash
uv run --with tiktoken python evals/measure.py
```

That reads the committed snapshot and prints median, mean, min, max and standard deviation across prompts. It needs no API key. Regenerating the snapshot with `evals/llm_run.py` does need a logged-in `claude` CLI, and calls the model once per prompt and arm.

It measures length, not correctness. A skill that answered `k` to everything would win it. Token counts use `tiktoken`'s `o200k_base`, which is an approximation of any non-OpenAI tokenizer, so the ratio between arms is the meaningful part and the absolute counts are estimates. [Numbers and limits](/docs/counting) has the rest.
